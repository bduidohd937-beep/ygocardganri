# P0.5 성능 기준 · V0.1

기존 C안 디자인과 카드 설계 승인 흐름은 변경하지 않고, 데이터 규모 증가 시의 반응성과 저장 안정성을 개선한다.

## 기존 기준선 (2026-11-11, GitHub Actions CI)
- Vite 결과: JS 290.54 KB / gzip 87.79 KB; CSS 36.26 KB / gzip 8.93 KB
- CI: 기존 타입 검사·9개 단위 테스트·프로덕션 빌드 성공
- 위 수치는 **빌드 산출물 크기**로서 사용자 기기의 LCP·INP·메모리 사용량을 직접 측정한 수치가 아니다.

## 이번 성능 변경
1. 검색용 정규화 인덱스를 카드/세계가 변경될 때 재작성하고, 검색어 입력 때는 인덱스를 재사용한다. `useDeferredValue`로 긴 목록 검색을 후순위 렌더링한다.
2. 카드 라이브러리 최초 렌더를 60개, 변경 이력을 80개로 제한하고 버튼을 통해 추가 표시한다. 결과 전체 수는 그대로 표시한다.
3. 연속 편집 시 IndexedDB 쓰기를 450ms 단위로 합치고, 쓰기는 순차 처리한다. 탭 숨김/페이지 이탈 시 즉시 저장을 시도한다. **페이지 종료 중 비동기 저장 완료는 보장할 수 없다.** 백업 기능은 그대로 제공한다.
4. 카드 썸네일 이미지는 지연 로딩하고 디코딩을 비동기로 한다.
5. gzip JS 115 KiB / CSS 16 KiB를 CI 회귀 예산으로 둔다. 이는 성능을 위한 가드레일이지 실제 Web Vitals 기준이 아니다.
6. 100/1,000/10,000장 **합성 카드** 인덱싱·검색·목록 제한 테스트로 알고리즘 회귀를 감시한다.

## 별도로 필요한 브라우저 측정
- 실제 GitHub Pages 주소가 활성화되면 Chrome Lighthouse 모바일/PC, LCP/INP/CLS, 최초 렌더링, 긴 작업(long tasks), 메모리 프로파일링을 측정한다.
- 대량 이미지/CDB/Lua 업로드는 P2에서 Web Worker·메모리 제한·취소·진행률과 함께 별도 벤치마크한다.
- 목표: LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하 (현 단계에서 달성 여부 **미확인**).
- 10,000장 전체 렌더링 또는 파일 업로드 실전 검증을 통과했다고 표시해서는 안 된다. 현재는 합성 검색/목록 게이트만 검증한다.
