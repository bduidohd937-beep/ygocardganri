# P4.3 — ①·②·③ 번호별 효과와 Lua 이펙트·콜백 연결

## 구현 목표

기존 P4(정적 파일 검수), P4.1(AST 연결·수정 제안), P4.2(카드 전체 4단계 비교)를 유지하면서 **번호 효과 단위의 정적 연결 지도**를 별도로 추가한다.

1. CDB 또는 사용자 승인 효과의 `①:`, `②:`, `③:` 구간을 분리한다. `이 카드명의 ①의 효과는` 같은 공통 문구는 번호 효과 시작으로 해석하지 않는다.
2. Lua 5.3 AST에서 `initial_effect` 내 `Effect.CreateEffect`, `:RegisterEffect`, 개별 `:SetOperation`, `:SetCost`, `:SetTarget`, `:SetCondition`을 수집한다.
3. `SetOperation(s.name)`에서 `function s.name(...)`로 이어지는 선언과 내부 `Duel.*` 직접 호출을 파악한다.
4. 검색·파괴·특수 소환·제외 등 **고유하고 충돌하지 않는 처리 함수 근거**가 있는 경우에만 번호 효과와 Lua 이펙트 변수의 연결 후보를 제시한다.
5. 원문에 번호가 하나뿐이고 직접 등록된 객체가 하나뿐이되 처리 근거가 없는 경우 `단일 구조 후보`로 명시한다. **`e1 == ①` 같은 순서 규칙은 사용하지 않는다.**
6. Clone, 복수 Lua 원본, 중복 등록, 보조 헬퍼 사용, 서로 다른 CDB 원문, 파서 오류, 같은 처리 방식의 반복은 연결을 보류하고 `판별 불가`로 표시한다.
7. 연결한 후보에 한해 조건·코스트·대상·처리 단계의 직접 호출 여부와 해당 코드 행을 표시한다. 누락 의심은 `EFFECT_STAGE_REVIEW`로만 기록하고 확정 오류 판정하지 않는다.
8. 결과는 별도 `effectLinks` 배열로 보고서 JSON에 함께 보관한다. 승인 효과·검수 상태·CDB·Lua 원본을 수정하지 않는다.

## 품질/성능

- 기존 검수와 같이 테마별 최대 200장, 카드당 Lua 3개, Lua 원문 최대 128KiB. 범위 밖은 미확인 상태다.
- AST 파서는 전용 Worker에서만 불러오고, 카드 한 장의 P4.1/P4.2/P4.3 검사를 진행하는 동안 최대 3개 AST만 캐싱한다. 카드별 종료 후 캐시 비움.
- 정적 소스의 `Duel.SendtoHand`가 발견돼도 실제 실행 가능성, 카드 위치, 대상, 체인 타이밍, OCG 처리 순서가 일치하는지는 검증할 수 없다.
- 카드 텍스트 추론과 처리 함수 분류는 **보수적인 휴리스틱**이며, 미연결은 반드시 구현 오류라는 뜻이 아니다.
- 복수 효과가 동일하게 패에 넣는 경우 연결을 정하지 않는다. 실제 EDOPro 재정 검토·실전 회귀 테스트는 별도 P6 단계.

## 검증 대상

- ① 효과가 `e2`로, ② 효과가 `e1`로 구현돼도 고유 처리 함수로 추적
- 같은 처리 함수 둘의 임의 연결 금지
- Clone/다중 Lua/헬퍼에서 자동 연결 금지
- 공통 카드명 횟수 제한의 `①의`를 번호 효과 시작으로 오인하지 않음
- `SetCost`가 없는 유일한 연결 후보에서만 코스트 구현을 검토 대상으로 제시
- 실제 Chromium CDB + Lua 업로드, 번호별 분석·재접속·원본 보존
